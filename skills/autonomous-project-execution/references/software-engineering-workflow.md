# 软件工程流程

用于软件功能开发、跨模块重构和修复。按依赖顺序推进，各阶段由主任务依据已有授权作技术判断，不逐阶段等待用户批准。变更范围决定设计深度；现有架构、契约及项目流程充分时直接复用，只补实际变化。

## 1. 需求与验收

明确用户可观察结果、范围、必须保持的兼容性和验收场景；从代码与现有检查确认基线。影响产品行为的实质歧义再询问，独立准备继续。普通任务可用工作包表达；跨阶段或高风险项目才维护短计划。

涉及规模或性能时明确代表性数据量、增长预期及实际约束，按需选择延迟、吞吐、内存或外部调用成本作为验收指标。缺少指标时说明合理假设，不编造统一门槛；会改变架构或产品取舍时再澄清。

## 2. 架构与模块边界

先检查现有入口、依赖和数据流，再决定改动落在哪些模块、各自职责及允许的依赖方向。沿用现有架构，避免循环依赖、跨层直连或为了并行另造基础框架。

对相关风险明确处理方式：数据归属与生命周期、外部依赖、权限/信任边界、失败恢复，以及真实性能或运行限制。涉及持久化兼容时考虑迁移和回退；不为无关风险增设流程。

产出是足以指导实现的边界决定，可体现在已有模块、简图、短设计说明或 ADR。不能只创建目录就声称架构完成，也不要求每次新建架构文档。

## 3. 接口契约

在依赖实现启动前确定共享输入/输出、数据类型与约束、错误语义、状态变化和兼容要求。跨服务或外部边界再补相应鉴权、超时、重试/幂等；无此边界则不强加。

使用项目已有权威形式：语言类型/函数签名、schema、OpenAPI、protobuf 或已有规范；文档引用它，不手抄维护另一套定义。提供能消除歧义的成功与失败示例，必要时用契约测试固定行为。

共享契约由一位负责人维护。只有其稳定范围内的工作才进入并行实现；其余可先探索。变更契约时同步所有消费者和相关测试，不能让前后端或两个代理各自猜字段。

## 4. 并行实现

按模块/文件和运行资源拆工作包，明确依赖、接口、授权边界和验收。每位负责人完成自己的实现及相关测试；主任务处理共享基础、关键路径与集成。公共类型、schema、锁文件、全局配置及同一写入资源不能同时改。

先打通最小真实主路径，再补错误处理和边界情况。Mock/占位须遵循已定契约，只用于隔离开发或测试，不能冒充已完成真实集成。详细交接规则见 [并行执行与交接](autonomous-execution-workflow.md)。

### 实现质量与执行效率

功能正确、边界完整和失败可恢复是前提；实现还须在目标规模内高效运行且便于维护。性能约束在架构阶段识别，算法选择在实现前判断，完成后以验收确认。

- **算法与数据结构**：按输入规模、分布和访问模式比较可行方案，关键路径说明时间/空间复杂度及取舍。选择不明或规模使朴素方案不可行时，查权威资料、比较成熟实现或用小型原型验证；优先可靠的标准库与成熟库，不凭直觉堆循环、缓存或并发。
- **实际开销**：关注重复扫描、N+1 查询、重复 I/O、不必要的数据复制以及无界内存/并发。复杂度分析与实际运行开销都要看；索引、批处理、流式处理或并发按瓶颈采用，新增缓存须处理一致性与生命周期，不能用资源堆叠掩盖算法问题。
- **清晰结构**：模块和函数职责集中，命名反映业务语义，数据流及依赖可追踪。避免混杂业务与基础设施的大函数、散落的重复逻辑、隐式全局状态、层层特判及无必要的嵌套；在本次改动边界内整理，不借“优雅”重写无关代码。
- **克制抽象**：复用明确稳定的共性，保留有意义的业务差异。抽象层、设计模式和依赖应减少理解与修改成本；不追求最少行数、炫技表达式或固定函数长度。性能必要的复杂实现保留简短的取舍说明，便于后续验证与修改。
- **有证据的优化**：改动影响复杂度或资源开销、需验证规模/性能目标或处理性能问题时，建立可复现基线，定位瓶颈并比较方案。记录代表性输入、环境、命令及相关耗时/吞吐/内存，覆盖必要的大规模或最坏分布；保留同等正确性与边界验证，不以单次微基准宣称整体提速。没有上述影响的普通局部修改检查复杂度与开销即可，无需额外测量或搭建基准平台。

## 5. 测试与集成

按行为和风险选择检查，完成项目规定的必要检查；不固定覆盖率、测试数量或每次全套命令。

| 变化 | 最少需要证明的内容 |
| --- | --- |
| 业务逻辑或缺陷修复 | 相关规则、边界和原失败场景；适合自动化时加入回归测试，能复现时先确认旧实现失败 |
| 模块/接口/数据格式 | 生产者与消费者兼容、输入约束和错误语义；检查真实连接，不能只有同假设的两套 mock |
| 存储、迁移或有副作用操作 | 相关约束、失败恢复及重复执行行为；用隔离数据验证，不使用真实用户数据 |
| 用户主流程/关键 UI | 对受影响关键路径做集成或端到端验证，覆盖相关失败状态；视觉改动还需真实渲染检查 |
| 构建、依赖或配置 | 受影响的解析、类型、构建或启动路径；生成物与配置来源一致 |
| 影响复杂度/资源开销的改动，或需验证规模/性能目标 | 相同语义与边界下的复杂度依据、代表性规模测量及相关资源开销；对明确性能目标提供可复查结果 |
| 纯文案、格式或低风险机械修改 | 相应 diff、语法或链接检查；不写复述实现的测试 |

并行测试使用独立数据库、端口和输出目录，或串行执行冲突检查；避免共享缓存污染和时序偶然通过。汇合后验证当前集成主路径，相关共享变更会使旧局部证据失效，只补跑受影响检查。

失败先区分实现、环境或错误测试；修正测试须说明与需求的冲突，并保留等效或更强验证。不得删除测试、弱化断言、跳过错误或缩减需求来制造通过。既有失败明确记录归因；必要检查无法完成时说明缺口，不把未验证记为通过。

## 目录与临时文件

沿用项目现有布局。新项目只建立实际需要的目录：生产源码、测试/fixtures、运维脚本、必要文档各有明确职责；生成物/缓存/临时产物与源码分离，路径命名遵循技术栈惯例。不要为“标准化”重排成熟仓库，也不预建空目录或无职责的抽象层。

一次性中间文件优先使用系统临时目录，必须留在项目内时放项目约定的任务独占临时子目录，例如 `.tmp/<task>/`；避免根目录堆放 scratch 脚本、日志、截图和导出文件。用临时目录上下文、try/finally 或 shell trap 安排清理，用完即删；进程被强杀后的遗留由接续任务核实归属后清理。

只清理本任务创建且已不用的路径和进程，不删除用户原文件、同伴产物、持久 fixture 或可复用工具。交付/调试所需证据保存在指定产物目录并说明用途，其余临时内容清除；gitignore 不能替代清理。清理失败如实说明路径和原因，不称目录已干净。

## 完成条件

请求范围已实现，架构/契约/消费者一致，必要验收对应当前集成状态；实现满足已定性能约束，受影响代码没有未处理的明显复杂度退化或无依据的结构复杂化，自有临时产物及无关进程已清理。交付说明实际变化、验证、必要的性能/结构取舍、已知限制及保留产物；未满足的项明确为未完成或阻塞。提交、推送、发布等继续依各自授权执行。
