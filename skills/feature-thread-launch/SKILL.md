# Feature Thread Launch

## 概览

这个 skill 用于主线程需要保持项目控制面，而具体实现任务应下沉到独立功能线程的场景。

它刻意保持轻量，目标是可靠启动功能线程，而不是把交接变成繁琐流程。

核心分层：

- 主对话负责需求、文档、目标、验收和归档。
- 子对话负责一个明确交付单元。
- 子代理负责子对话内部的降噪与并行。

## 适用场景

适合使用：

- 主线程已经识别出一个具体实现任务
- 任务会产生日志、多轮编辑、调试循环或高噪音验证
- 任务应隔离到功能线程中，最好放入 worktree
- 用户希望主线程上下文保留给项目控制
- 用户希望功能线程用性价比高、速度快且足以完成任务的模型配置

不适合使用：

- 当前只是低噪音的小型控制面编辑
- 任务仍然过于模糊，无法定义有边界目标
- 仓库尚未初始化为项目级工作流

## 必要启动信息

启动包应保持最小但足够：

- 有边界的目标
- 验收标准
- 相关文件或目录
- 必须保持不变的约束
- 必要时说明 worktree 偏好
- 必要时说明模型偏好，例如优先使用轻量快速模型，复杂验收再回主线程

功能线程默认先判断哪些探索、归因、扫描或总结工作适合交给子代理；若任务极小或不存在可独立拆解项，可以明确不派。

## 启动流程

1. 确认任务不应继续留在主线程。
2. 定义一个有边界的功能线程目标。
3. 定义贴近真实交付路径的验收标准。
4. 指明相关代码区域和已知风险。
5. 对长任务、高噪音任务或无人值守任务，优先使用 worktree。
6. 默认让功能线程选择足够可靠、性价比高、速度快的模型，不把最强模型当成落地执行默认值。
7. 要求功能线程尽早使用子代理做探索、日志归因、测试缺口扫描、风险扫描和首轮 review。
8. 要求功能线程回传简短摘要，包含验证证据、变更文件、goal delta 和已知限制。

## 基本规则

- 启动包要短、可执行。
- 先推进框架和主交付路径，再补细节。
- 不要让文档、边界抛光或过度测试扩展阻塞主功能路径。
- 如果功能线程陷入局部优化，应快速纠偏 goal 或 Stage Objective。
- 一个功能线程通常只保留一个主要写入路径。
- 子代理并行读，主执行者单点写，主线程只吸收摘要和验收证据。
- 子代理不是长期记忆层，也不替代主线程做方向判断。

## 预期结果

使用该 skill 后，主线程应保留项目级控制上下文，功能线程则以低噪音方式执行一个有边界的交付单元。

如果启动包变得冗长、含糊或塞入过早细节，说明交接过重，需要收敛。
