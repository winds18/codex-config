# 项目初始化展开流程

这份文档定义：如何基于全局 `AGENTS.md`，把一个新项目展开为项目级可执行文档体系。

适用场景：

- 新项目从零开始
- 个人开发
- Codex 主导执行
- 偏无人值守
- 尽量减少重复说明

---

## 1. 目标

全局 `AGENTS.md` 负责长期不变的总规则。

新项目启动后，不应直接把全局文件整份复制进仓库，而应将其展开为一组更具体、更短、更贴近仓库现实的项目文档。

展开后的项目文档必须回答以下问题：

- 这个项目要做什么
- 当前阶段先做什么
- 项目怎么运行
- 项目怎么测试
- 项目有哪些局部约束
- Codex 在这个项目中何时应自动推进，何时必须停下来
- 主对话、功能线程和子代理如何分工

---

## 2. 展开原则

- 全局文件负责哲学、方法、默认策略。
- 项目文件负责命令、目录、约束、交付、验证。
- 不复制大段抽象规则，只保留项目真正需要落地的内容。
- 所有项目文档都应尽量短、小、真、可执行。
- 默认执行顺序应体现“框架 / 主路径优先，细节 / 修饰后置”。
- 文档的职责是支撑推进，不是让初始化阶段先背上过重流程负担。
- 如果一条规则不能指导当前仓库中的具体行为，就不要写进项目文档。
- 项目文档、提交说明、执行总结和代码注释默认使用中文。
- 命令、代码标识符、协议字段、外部 API 名称和错误原文可以保留英文。

---

## 3. 推荐展开产物

新项目最少生成以下文件：

- `AGENTS.md`
- `README.md`
- `docs/spec.md`
- `docs/plan.md`
- `CHANGELOG.md`

按需生成以下补充文件：

- `docs/decisions/001-xxx.md`
- `docs/testing.md`
- `docs/review.md`
- `docs/deployment.md`
- `.codex/agents/*.toml`
- `.codex/config.toml`
- `.codex/hooks.json`
- `scripts/project-guard.sh`
- `git-hooks/`

---

## 4. 各文件职责

### `AGENTS.md`

负责项目级操作规则。

应包含：

- 项目定位
- 目录结构
- 运行命令
- 测试 / lint / build 命令
- 局部技术约束
- 默认验证顺序
- 项目中的少打扰规则
- 项目中何时必须升级给我
- 主线程与功能线程分工
- 功能线程归档规则
- 子对话默认模型策略
- 子代理降噪与并行边界

不要写：

- 过长的产品背景
- 大段全局哲学复述
- 临时任务计划

### `README.md`

负责给人类和 Codex 提供最短项目入口。

应包含：

- 项目是什么
- 本地如何启动
- 主要目录说明
- 当前进展概览

### `docs/spec.md`

负责定义项目使命、范围、阶段目标和不做什么。

应包含：

- Mission
- Constraints
- 当前范围
- 暂不处理的范围
- 阶段拆分
- 成功标准

### `docs/plan.md`

负责当前执行顺序。

应包含：

- 当前 Working Goal
- 阶段列表
- 每阶段交付物
- 每阶段验收条件
- 当前阶段优先级顺序
- 当前明确延后的细节项
- 当前 blockers
- 当前活跃线程总表
- 已完成待归档或已归档线程记录
- 功能线程内部的子代理拆解摘要

### `CHANGELOG.md`

负责记录稳定变化，不要求细碎。

应按阶段或里程碑记录：

- 新增
- 修改
- 修复
- 已知限制

---

## 5. 轻量文档信息表

长期维护的项目文档建议在标题后放一段轻量文档信息表。

推荐格式：

```markdown
## 文档信息

| 项目 | 内容 |
| --- | --- |
| 状态 | 生效中 |
| 最后更新 | YYYY-MM-DD |
| 适用范围 | 本项目 / 某模块 / 某阶段 |
| 关联入口 | AGENTS.md / README.md / docs/plan.md |
```

适合使用：

- `docs/spec.md`
- `docs/plan.md`
- `docs/testing.md`
- `docs/deployment.md`
- `docs/decisions/*.md`
- 长期治理类文档

不强制使用：

- `AGENTS.md`
- `README.md`
- `CHANGELOG.md`
- skill `SKILL.md`
- 临时记录
- 自动生成文件

规则：

- 表头只用于判断文档状态、适用范围和入口关系。
- 不要把表头扩展成审批流、复杂版本历史或长维护记录。
- 如果表头字段无法真实维护，宁可不加。

---

## 6. 初始化标准流程

新项目启动时，默认按以下顺序展开：

1. 创建 Git 仓库
2. 明确 Mission 与 Constraints
3. 生成项目级 `AGENTS.md`
4. 生成 `README.md`
5. 生成 `docs/spec.md`
6. 生成 `docs/plan.md`
7. 生成 `CHANGELOG.md`
8. 初始化 `.codex/` 相关配置
9. 明确最小运行、测试、构建命令
10. 定义主线程与功能线程治理规则
11. 定义子对话模型策略与子代理拆解边界
12. 再进入第一阶段实现

不要跳过文档直接写代码。

不要在目录、命令、验证标准尚未明确前进入无人值守实现。

不要在骨架和主路径尚未明确前，就把大量时间投入到文档扩写、测试铺满或局部修饰。

---

## 7. 推荐初始化提问顺序

当 Codex 基于全局规则展开新项目时，应优先确定以下内容：

1. 这个项目最终要交付什么
2. 第一版最小可用范围是什么
3. 不做什么
4. 技术栈偏好是什么
5. 本地运行方式是什么
6. 最低验证标准是什么
7. 哪些操作必须中断询问
8. 哪些工作必须新开功能线程处理
9. 功能线程默认用什么模型策略
10. 子代理默认承担哪些降噪和并行任务

如果这些答案不完整，先生成最小版本，再在执行中补全，不要因为追求完美前置定义而卡住启动。

---

## 8. `.codex/` 目录建议

如果项目会长期使用 Codex，建议尽早建立：

- `.codex/config.toml`
- `.codex/agents/`
- `.codex/notes/`

推荐用途：

- `config.toml`：项目级默认行为、功能开关、局部配置
- `agents/`：项目级子代理角色
- `notes/`：供 Codex 使用的局部补充说明
- `hooks.json`：项目级高风险动作守门点

需要配置权限 glob 时，参考 `docs/project-codex-config-template.md`，按项目实际情况选择性写入 `.codex/config.toml`。不要覆盖机器级 `~/.codex/config.toml`，也不要把与项目无关的全局配置复制进仓库。

项目级 hook 不要求一开始就完整设计。

优先只覆盖：

- secret 防泄露
- 危险命令阻断
- 提交 / 推送前 guard 提醒
- 完成声明前的验证提醒

---

## 9. Goal-first 展开要求

项目展开时，必须把全局 Goal 模型映射到项目级文档里：

- `Mission` 写入 `docs/spec.md`
- `Constraints` 写入 `AGENTS.md` 与 `docs/spec.md`
- `Working Goal` 写入 `docs/plan.md`
- `Stage Objective` 写入 `docs/plan.md`

不要只写功能清单。

必须让 Codex 能区分：

- 最终目标是什么
- 当前目标是什么
- 当前阶段是什么
- 哪些可以改
- 哪些不能改

---

## 10. 无人值守展开要求

如果项目目标是偏无人值守，项目级 `AGENTS.md` 必须明确以下内容：

- 默认自动推进到什么程度
- 哪些情况必须暂停
- 是否允许自动 commit
- 是否允许自动创建 PR
- 是否允许自动引入依赖
- 是否允许自动升级权限
- 失败多少次后必须中断
- 主对话是否禁止直接做功能开发
- 子对话默认使用什么模型策略
- 功能线程何时必须归档

没有这些规则，不要假设系统能安全无人值守。

---

## 11. 子代理展开要求

如果项目会使用子代理，项目级文档中至少应明确：

- 哪些任务适合派子代理
- 哪些任务不允许并发写
- 哪些子代理只读
- 哪些子代理可写
- 哪些子代理适合轻模型
- 哪些子代理必须强模型
- 功能线程是否默认先用子代理做侦察、归因、总结

默认分层应写清：

- 主对话负责需求挖掘、文档周期、目标管理、验收、合并和归档
- 子对话负责一个明确交付单元，优先使用性价比高、速度快、足以完成任务的模型
- 子代理负责子对话内部的降噪与并行，优先读多写少，返回摘要和证据

建议先从少量明确角色开始，不要一开始就设计过多代理。

---

## 12. Worktree 展开要求

如果项目将长期无人值守执行，项目级文档中应明确：

- 什么任务默认进 worktree
- 什么情况下 handoff 回 Local
- 依赖初始化如何在 worktree 自动执行
- 哪些文件或缓存不会随 handoff 移动
- 功能线程是否默认在 worktree 中创建
- 如果项目启用 Git hooks，每个 worktree 内如何安装 hooks

---

## 13. Git 工作流展开要求

项目级文档应明确最小 Git 工作流。

至少包含：

- 默认分支策略
- 是否使用功能分支或 worktree
- 提交信息格式
- 提交前验证命令
- 是否启用 Git hooks
- Git hooks 安装命令
- 每个 worktree 是否需要单独安装 hooks
- 版本发布方式
- 构建产物存放位置和是否入库

默认提交前顺序：

1. 查看 `git status` 和相关 diff
2. 确认本次提交边界
3. 暂存同一目的下的相关改动
4. 运行项目验证或 guard
5. 同步关键文档
6. 再提交

版本号、emoji、`commit-msg` 校验、发布分支策略只在项目确实需要时启用。

不要把团队发布仓库的完整版本规则默认复制到所有个人项目。

项目级发布规则至少应说明：

- 版本事实源在哪里
- 是否使用 SemVer
- tag 格式
- 发布前完整验证命令
- 构建产物生成命令
- 构建产物发布或归档位置
- 哪些产物禁止提交进源码仓库
- 临时文件目录和提交前清理命令

如果项目暂不发布，明确写“暂不发布”，不要提前设计复杂发布流程。

默认临时目录建议：

- `.tmp/`
- `.artifacts/`
- `.cache/`

这些目录应进入 `.gitignore`。

如果项目启用 guard 或 Git hooks，应在提交前检查暂存区没有临时目录内容、日志、备份文件或一次性中间文件。

---

## 14. 守门点展开要求

如果项目需要更可靠的无人值守执行，可以建立轻量守门点。

推荐顺序：

1. 先在项目级 `AGENTS.md` 写清必须遵守的核心节点
2. 再创建 `scripts/project-guard.sh` 检查确定性事实
3. 最后按需创建 `.codex/hooks.json` 和 Git hooks

适合硬拦的项目级节点：

- 明显破坏性命令
- secret 或凭证外泄
- 直接修改受保护生成物
- 提交或推送前未运行项目 guard

不适合硬拦的项目级节点：

- 产品方向判断
- 功能是否“足够好”
- goal delta 是否语义正确
- 是否应该继续打磨某个细节

这些仍由主编排线程结合 `docs/plan.md`、功能线程摘要和验收结果判断。

不要在项目主路径尚未打通前，为了 hook 而设计复杂 hook。

---

## 15. 何时拆更多文档

只有以下情况才建议继续拆文档：

- 某块规则在 `AGENTS.md` 中已经过长
- 某部分架构决策需要单独追踪
- 测试或部署逻辑已经明显复杂
- 代码审查规则需要长期复用

如果项目还很小，宁可少文档，也不要为“看起来完整”而过度拆分。

---

## 16. 每次新项目的执行提示词

可以在新项目开始时直接对 Codex 使用类似指令：

```text
基于我的全局 AGENTS.md，初始化这个新项目。
请先不要直接写业务代码，而是先展开项目级文档体系。

要求：
1. 生成项目级 AGENTS.md
2. 生成 README.md
3. 生成 docs/spec.md
4. 生成 docs/plan.md
5. 生成 CHANGELOG.md
6. 如有必要，初始化 .codex/ 目录

请把全局规则转化成项目内可执行的具体规则，不要整份照抄全局总纲。
```

---

## 17. 完成标准

一个新项目完成“初始化展开”，至少应满足：

- 有项目级入口文档
- 有项目级操作规则
- 有阶段计划
- 有最小验证路径
- 有无人值守边界
- 有主线程 / 功能线程治理规则
- 有功能线程内部的子代理拆解规则
- 有最小 Git 工作流与提交前整理规则
- 有必要时才有轻量 guard / hook 守门点
- 有清晰的下一步实现目标

只有满足这些条件后，才适合进入真正的自动化实现阶段。
