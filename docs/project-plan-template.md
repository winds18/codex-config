# `docs/plan.md` 模板

下面是一份面向你当前这套治理模型的 `docs/plan.md` 模板。

目标：

- 让主线程能持续把控项目节点
- 让功能线程状态有固定落点
- 让功能线程内部的子代理拆解结果也能被记录

使用方式：

- 保留结构
- 替换占位项
- 删除不适用内容
- 保持它比 `spec` 更动态、更偏执行面

## 5. 开发优先级守则

当前阶段默认优先级：

1. 先打通框架、骨架或最小主路径
2. 再完成主要功能板块
3. 再补细节、边界情况和增强项
4. 最后再做修饰、抛光和非关键优化

当前阶段应明确写出：

- `[当前必须先打通的主路径]`
- `[当前明确延后的细节项]`
- `[当前明确不做的修饰项]`

如果主路径尚未打通，不应优先把精力投入：

- 大而全测试补齐
- 大量说明文档扩写
- 局部细节长时间打磨
- 非关键区域过度重构

---

## 6. 功能线程交付要求

每个功能线程完成时，至少应向主线程回报：

- 线程目标
- 实际完成内容
- 验证证据
- 变更范围
- 是否发生 goal delta
- 已知限制
- 后续事项

主线程只有在这些信息充分时，才应做验收与合并决策。

默认原则：

- 功能线程应尽量先拆出高噪音工作给子代理
- 子代理优先返回摘要
- 主执行者只保留真正需要进入实现上下文的信息

---

## 8. 验收与合并清单

主线程在验收功能线程时，至少检查：

- 目标是否达成
- 验证是否通过
- 文档是否同步
- 已知限制是否说明
- 是否可以合并
- 合并后是否应立即归档
- 是否在正确优先级上先打通了主路径，而不是过早陷入细节或修饰
